# Vekaro — інформаційний веб-сайт

## Бізнес-контекст

**Vekaro** — компанія з оренди легкових авто, працює тільки у Варшаві (Польща).

Сайт — чиста "візитка" (brochure site): без онлайн-бронювання, без входу в акаунт.
Мета сайту — інформація + контакти, щоб клієнт зателефонував або написав у месенджер.

### Напрямки бізнесу

1. **Короткострокова оренда** — від 24 годин до місяця
2. **Довгострокова оренда** — від місяця, ціна за запитом
3. **Комерційна оренда** — для кур'єрів/доставки, без деталізації умов, просто "телефонуйте"
4. **B2B / підмінні авто** — страхові компанії, інші фірми, юрособи, без деталізації умов, просто "телефонуйте"

### Автопарк

Зараз: **Fiat Tipo**, **Skoda Citigo** (список буде розширюватись).
Ціни — орієнтовно "від 50 zł/доба", без детального прайсу на сайті.

### Мови сайту

- Польська (**pl**) — основна
- Англійська (**en**)
- Українська (**uk**)

### Контакти

- Телефон: **+48 789 085 345**
- Месенджери: WhatsApp, Telegram, Instagram
- QR-код на рекламних матеріалах
- Робочі години: **8:00–18:00**
- Кнопка дзвінка замість форми заявки (для комерційної та B2B оренди — без форми, тільки кнопка дзвінка)

### Юридичне

- NIP поки не вказуємо (уточнюється з клієнтом)
- Без REGON
- Потрібна сторінка Polityka prywatności (Політика приватності)

## Структура сторінки

Референс — sixt.pl, спрощено під наш кейс.

Порядок секцій свідомо не збігається з номерами нижче (перелік — це опис контенту, порядок на
сторінці описано окремо після списку).

1. **Header** — лого, меню, перемикач мов PL/EN/UK, телефон/WhatsApp одразу видимі
2. **Hero** — заголовок, фото авто, кнопка дзвінка
3. **Слоган-банер** — головний меседж + "від 50 zł/доба"
4. **`Services`** (`<section id="services">`, `src/components/sections/Services/`) — об'єднаний розділ,
   ОДНА обгортка-секція з одним якорем:
   - **Три картки напрямків оренди** (H2 "Nasze usługi") — короткострокова / довгострокова / для
     бізнесу (комерційна + B2B об'єднані)
   - **Автопарк** (H3 "Nasza flota" + короткий підзаголовок) — 4 картки (Fiat Tipo, Skoda Citigo ×2,
     поки реальних авто лише 2) на весь екран, референс blsrentcar.pl. **Більше не окрема секція** —
     підрозділ усередині Services, без власного якоря в хедері
5. **Три переваги** ("Why Vekaro") — іконки + короткий текст. Окрема секція (не входить у `Services`),
   **без власного якоря/кнопки в хедері** — так само, як "Про компанію" не має власного пункту меню
6. **Про компанію** — текст + фото офісу
   - *(додатково)* **`PromoBanner`** — функціональна промо-секція одразу після "Про компанію", перед
     контактами: фото авто + заголовок/підзаголовок/кнопка "Zadzwoń teraz" (`tel:`). Не акційний банер
     (знижки зараз немає), просто заклик до дії; має необов'язкове поле `badge` про запас, щоб пізніше
     легко додати бейдж знижки — **новий контент, замінив декоративний `CarShowcase`**
7. **Контакти** — телефон, месенджери, QR-код, робочі години, мапа "тільки Варшава"
   - *(додатково)* **FAQ-акордеон** (4 питання-відповіді) замінив пунктирний плейсхолдер-блок
     "мапа" — **новий контент**, розгортається/згортається по кліку, один розділ відкритий одночасно
8. **Footer** — посилання на напрямки, соцмережі, юридичне, Polityka prywatności

**Фактичний порядок на сторінці** (`src/app/[locale]/page.tsx`): Header → Hero → Слоган-банер →
**`Services`** (Напрямки оренди + Автопарк, одна секція) → Переваги → Про компанію → PromoBanner →
Контакти (+ FAQ) → Footer.

**Якорі в хедері** (3, не 4): `#services` ("Oferta"/"Services"/"Послуги" — веде на об'єднаний розділ
послуг+автопарку), `#about`, `#contact`. У "Переваги" й "Про компанію" немає власного пункту меню.

### Сторінки послуг (`/services/*`)

Сайт більше не суто односторінковий — кнопки на трьох картках напрямків оренди (`RentalTypeCard`)
тепер ведуть не на `tel:`, а на окремі сторінки з детальним описом кожного напрямку:

- `/services/short-term` — короткострокова оренда — **повністю наповнена контентом** (див. окремий
  підрозділ нижче)
- `/services/long-term` — довгострокова оренда — **повністю наповнена контентом** (див. окремий
  підрозділ нижче)
- `/services/business` — для бізнесу/B2B — **повністю наповнена контентом** (див. окремий підрозділ
  нижче)

Усі три сторінки тепер мають власні компоненти (спільного шаблону-заглушки `ServiceDetail.tsx` більше
немає в кодовій базі — видалений як мертвий код, коли останній його користувач, `/services/business`,
перейшов на власний компонент). Метадані (title/description/hreflang/canonical) для всіх трьох сторінок
генерує спільний хелпер `src/lib/servicePageMetadata.ts` (приймає вже готові title/description, а не
сам їх шукає — щоб однаково обслуговувати `shortTermPage.hero.*`/`longTermPage.hero.*`/
`businessPage.hero.*`), щоб не дублювати логіку hreflang тричі. `src/app/sitemap.ts` віддає 12 URL
(4 шляхи × 3 мови) з коректними alternates.

**Хлібні крихти** (`src/components/ui/Breadcrumbs/Breadcrumbs.tsx`): іконка "додому" (посилання на `/`)
+ роздільник `/` + назва поточної сторінки (текст, не посилання). Замінили попереднє текстове
посилання "← Powrót do oferty". Візуальний компонент сам собою SEO не дає — реальну користь для СЕО
дає структуровані дані поруч: `src/components/StructuredData/BreadcrumbJsonLd.tsx` рендерить
`BreadcrumbList` (schema.org) з абсолютними URL для кожного рівня, той самий патерн, що й
`LocalBusinessJsonLd`. Це дозволяє Google показувати ланцюжок крихт прямо в результатах пошуку
замість повного URL.

### Три сторінки послуг — повний контент (short-term / long-term / business)

Усі три сторінки послуг наповнені реальним (не тимчасовим) текстом і повною SEO-структурою, за
єдиним шаблоном:

- `/services/short-term` — власний компонент
  `src/components/sections/ServiceDetail/ShortTermRentalPage.tsx` (+ `ShortTermRentalPage.module.css`),
  переклади — namespace `shortTermPage`
- `/services/long-term` — власний компонент
  `src/components/sections/ServiceDetail/LongTermRentalPage.tsx` (+ `LongTermRentalPage.module.css`),
  переклади — namespace `longTermPage`
- `/services/business` — власний компонент
  `src/components/sections/ServiceDetail/BusinessRentalPage.tsx` (+ `BusinessRentalPage.module.css`),
  переклади — namespace `businessPage`

Усі три `.module.css`-файли скопійовані 1:1 один з одного для візуальної консистентності (той самий
патерн, що вже описаний у "Технічні нотатки" вище — навмисне дублювання CSS-модуля замість спільної
абстракції, бо це самостійні сторінки, а не варіанти одного компонента). Структура сторінки (порядок
блоків фіксований, однаковий для всіх трьох):

1. **Hero** — крихти-навігація, H1 (`hero.title`), короткий вступ 1-2 речення (`hero.description`,
   БЕЗ повного визначення — воно нижче в SEO-блоці), кнопка дзвінка
2. **Стрічка автопарку** — 2 картки (Fiat Tipo, Skoda Citigo — звичайні легкові авто навіть на
   business-сторінці, не комерційний/вантажний транспорт), перевикористано `FleetCard` з
   `src/components/sections/Fleet/` (та самі фото-заглушки й переклади з namespace `fleet`, без
   дублювання 4 карток, як на головній — тут рівно 2 реальні авто). На кожній картці кругла
   кнопка-стрілка веде на `tel:`, а не "обрати авто"
3. **SEO-текстовий блок** — 4 підрозділи, кожен зі своїм `<h2>`: визначення (суцільний текст),
   два списки як **картки** (`#f2f1ee`, заокруглені кути, на десктопі поруч — short-term "Kiedy
   warto"/"Dlaczego Vekaro" по 4 пункти, long-term "Kiedy warto wybrać..."/"Dlaczego Vekaro" по
   4 пункти, business "Dla kogo jest ta oferta?" (3 пункти) / "Dlaczego Vekaro" (4 пункти) —
   кількість пунктів у картках навмисно нерівна, verstka не залежить від кількості), "Jak to działa"
   (3 кроки, нумеровані помаранчевими кружечками через CSS `counter`, вирівняні по центру flexbox'ом
   відносно тексту)
4. **FAQ** — перевикористано існуючий клієнтський компонент `Faq` (`src/components/sections/Contact/Faq.tsx`,
   з плавною grid-based анімацією розкриття). **short-term** ділить той самий набір питань, що й на
   головній (namespace `faq`, спільний з `Contact`). **long-term** і **business** мають кожен власний
   окремий набір питань (`longTermPage.faq`/`businessPage.faq` — довгострокова: мінімальний термін,
   фіксована ціна, сервіс/страховка, виїзд за кордон; бізнес: які компанії, підмінні авто для
   страховиків, процес підписання договору, оренда кількох авто одразу)

Семантика всіх трьох сторінок: один `<h1>`, п'ять `<h2>` (4 SEO-підрозділи + FAQ), перевірено через
`curl`-вивід. `BreadcrumbJsonLd` теж рендериться на кожній (`title`/`path` беруться з відповідного
`hero.title` і локального `PATH`).

Текстовий стиль усіх трьох сторінок: без тире (—/–) для розділення частин речення — свідоме рішення,
речення переформульовані через кому/крапку замість тире (перевірено скриптом по кожному namespace
окремо, щоб не зачепити em-dash в інших частинах сайту, де він лишається стилістичною нормою, напр.
`hero.subtitle`, `sloganBanner`, `advantages`).

Оскільки всі три сторінки відокремились у власні компоненти, спільний шаблон-заглушка
`src/components/sections/ServiceDetail/ServiceDetail.tsx` (і його CSS-модуль) втратив останнього
користувача і був **видалений повністю** — не мертвий код, а фактично прибраний, коли в ньому
відпала потреба.

**Наслідок для архітектури:** `Header`/`Footer`/`CookieBanner` переїхали з `page.tsx` у спільний
`src/app/[locale]/layout.tsx` (раніше рендерились тільки на головній, бо сторінка була одна). Нав-посилання
в `Header` (`services`/`about`/`contact`) тепер `Link href="/#services"` замість `<a href="#services">` —
працюють однаково і з головної, і з будь-якої `/services/*` сторінки. Спільний `Button`
(`src/components/ui/Button/Button.tsx`) тепер вміє два типи посилань: зовнішні (`tel:`/`mailto:`/`http(s):`)
рендеряться як звичайний `<a>`, внутрішні — як next-intl `Link` (щоб зберігати локаль при переході).

**Виправлений побічний ефект:** оскільки `Header` тепер не перемонтовується між сторінками однієї локалі,
його internal scrollspy-стан (`activeSection`) міг лишатися "залипшим" на `services` при переході на
сторінку без відповідних `id`-секцій (напр. `/services/short-term`), підсвічуючи "Oferta" помаранчевим
там, де це вже не має сенсу. Виправлено: `useEffect` зі scrollspy тепер залежить від `usePathname()` і
переініціалізується при кожній зміні шляху; сам клас `.navLinkActive` додатково перевіряє
`pathname === "/"`, тож на сторінках без секцій підсвітка ніколи не показується, навіть якщо стан ще
не встиг оновитись.

Логіка порядку: спершу відповідаємо на "чи закриєте ви мій запит" (напрямки оренди), одразу
підкріплюємо конкретикою "на чому саме поїду" (автопарк) — це найважливіші рішенневпливові блоки
одразу після Hero. "Чому обрати нас" і "про компанію" — довіра/бекграунд для тих, хто вже зацікавлений
і скролить далі, тож вони йдуть нижче, ближче до контактів.

## Технічні нотатки

### Кольорова схема

Фіксована (не залежить від системної теми ОС — `prefers-color-scheme` більше не використовується):
чорний фон/білий текст на Header і Hero, білий фон/темний текст на всьому контенті між Hero і Footer,
знову чорний на Footer. Реалізовано через глобальний клас `.theme-dark` (`globals.css`) — локально
перевизначає `--background`/`--foreground`/`--gradient-spot`, застосований на `Header`, `Hero`, `Footer`.
Усі інші компоненти самі нічого не знають про тему — просто використовують `var(--foreground)`/
`var(--background)`, тож автоматично підхоплюють правильні кольори залежно від того, в якій секції
опинились.

### Header при скролі (sticky + блюр)

`Header` завжди `position: sticky; top: 0`. На самому верху сторінки — суцільний чорний фон
(`.theme-dark`, той самий механізм, що й у `Hero`/`Footer`). Щойно `window.scrollY > SCROLLED_THRESHOLD`
(**100**, див. нижче чому не 8) — вмикається клас `.scrolled` (напівпрозорий чорний, `rgba(10,10,10,0.6)`)
і **інлайновий** `style={{ backdropFilter: "blur(40px)" }}` у `Header.tsx`.

**Знайдений і виправлений баг №1:** селектор `.scrolled` спочатку був одиночним класом і програвав
каскад глобальному `.theme-dark` (обидва задають `background`, однакова специфічність — виграє той,
чий CSS опинився пізніше в зібраному бандлі, що на практиці виявилось `theme-dark`). Через це
прозорість при скролі візуально не працювала: `getComputedStyle` показував суцільний
`rgb(10,10,10)` замість очікуваного `rgba(10,10,10,0.6)`, хоча в CSS-файлі значення було правильним.
Виправлено підняттям специфічності через складений селектор `.header.scrolled` замість просто
`.scrolled` — тепер надійно перебиває `.theme-dark` незалежно від порядку в зібраному CSS.

**Знайдений і виправлений баг №2:** перші ~100px скролу хедер на секунду ставав світло-сірим
замість чорного/напівпрозорого чорного — виглядало, ніби під хедером з'являлась біла смуга.
Причина — артефакт `backdrop-filter: blur(40px)`: блюру потрібні реальні відрендерені пікселі НАД
хедером, щоб їх семплити, а біля самого верху документа (у перші ~100px скролу) таких пікселів ще
недостатньо — браузер добирає відсутнє прозорим/білим, і це блідо-сіре домішується в результат
рівномірно по всій ширині хедера. Перевірено емпірично через `getComputedStyle`/скріншоти на різних
`scrollY`: ще сіро на 60px, вже чисто чорно на 100px. Виправлено підняттям порогу активації
`.scrolled`+блюру з `scrollY > 8` до `scrollY > SCROLLED_THRESHOLD` (100) — без візуальних втрат,
бо в цьому діапазоні скролу під хедером все одно лише суцільно чорна `Hero`-секція, тож непрозорий
чорний хедер і напівпрозорий чорний хедер виглядають однаково.

**Іконки-кнопки в хедері** (телефон, WhatsApp, перемикач мов): суцільна помаранчева заливка
(`var(--accent)`), білий контент іконки (`color: #ffffff`, SVG використовують `stroke="currentColor"`),
без обвідки (`border: none`) — перевизначають базовий `IconButton.module.css` (який за замовчуванням
дає коло з обвідкою `border: 1px solid var(--foreground)` і прозорим фоном — цей варіант і далі
використовує, наприклад, стрілка на картці автопарку `FleetCard`, яка навмисно лишається
білою/чорною/з обвідкою, не помаранчевою).

**Чому блюр інлайном, а не в CSS-модулі:** зіткнулись із багом збірки Next.js 16.3 (Lightning CSS) —
при компіляції CSS-модуля властивість `backdrop-filter` губилась повністю, лишалась тільки
`-webkit-backdrop-filter`, яку сучасний Chrome вже не підтримує (немає навіть у
`CSSStyleDeclaration`). Не залежить від `browserslist` (пробували `"defaults"` — не допомогло).
Обхідний шлях — виставляти `backdropFilter` через inline `style`, це не проходить через
CSS-трансформацію збірки і працює коректно. Якщо колись оновите Next.js/lightningcss — варто
перевірити, чи баг ще актуальний, і за бажання повернути назад у CSS-модуль.

**Scrollspy (підсвітка активного розділу):** `Header.tsx` через `IntersectionObserver` стежить
за трьома секціями, що мають пункт у меню (`#services`, `#about`, `#contact` — інші секції, напр.
`Nasza flota`/`Dlaczego Vekaro`, у меню не винесені, тож не відстежуються). Спостерігач ловить
момент, коли секція перетинає вузьку смугу біля вертикального центру екрана
(`rootMargin: "-40% 0px -50% 0px"` — стандартний прийом для scrollspy), і додає клас
`.navLinkActive` (`color: var(--accent)`, той самий помаранчевий, що й у SloganBanner) відповідному
пункту меню. Колір винесено у глобальну змінну `--accent` (`globals.css`) — SloganBanner тепер теж
читає його звідти, а не тримає локальну копію.

**`LanguageSwitcher` отримав проп `direction?: "down" | "up"`** (за замовчуванням `"down"`, як і
раніше): футерний інстанс використовує `direction="up"`, щоб dropdown відкривався вгору
(`bottom: calc(100% + 8px)` замість `top: calc(100% + 8px)`) — інакше він виходив за межі viewport
знизу сторінки. Реалізовано через компаунд-селектор `.dropdown.dropdownUp` (не просто
`.dropdownUp`), той самий прийом, що й `.header.scrolled` — щоб гарантовано перебивати базовий
`.dropdown` незалежно від порядку в зібраному CSS. Header-інстанс не чіпали, лишається
`direction="down"` за замовчуванням.

**Знайдений і виправлений баг: dropdown футера вилазив за лівий край екрана на мобільному.**
Причина — горизонтальне позиціювання (`right: 0`) було статичним і розраховувалось відносно
тригера, а тригер футера на мобільному стоїть біля **лівого** краю (стек, `align-items: flex-start`
у `.bottomBar`), тоді як тригер у Header — біля **правого**. `right: 0` на кнопці, що сама стоїть
зліва, розкриває список ще лівіше — за межі viewport. Виправлено новим пропом
`align?: "left" | "right"` (за замовчуванням `"right"`, як і раніше): футерний інстанс —
`direction="up" align="left"`. Але сама горизонтальна позиція футера **не однакова на всіх
брейкпоінтах**: на мобільному `.bottomBar` — стек (тригер зліва), а від 1024px — рядок
(`justify-content: space-between`, тригер справа, як у Header). Тому `.dropdown.dropdownAlignLeft`
сама містить медіа-запит: `left: 0` за замовчуванням (мобільний), і `@media (min-width: 1024px)`
повертає `right: 0` (десктоп) — той самий один проп коректно працює на обох брейкпоінтах.
Перевірено через `getComputedStyle` на 1470px: `right: 0` застосувався, dropdown лишається в межах
viewport.

**Той самий баг був і в мобільному гамбургер-меню Header.** `LanguageSwitcher` там рендериться
всередині `ContactControls()` (спільна функція, викликається двічі — `.navContacts` для мобільного
випадного меню, `.desktopContacts` для десктопного верхнього рядка). У `.navContacts` (мобільна
панель на всю ширину, `justify-content` не задано → `flex-start`) тригер стоїть біля **лівого** краю,
на відміну від `.desktopContacts`, де він біля правого. `ContactControls` без пропів завжди
використовував `align="right"` за замовчуванням — правильно для десктопу, але ламало мобільне меню
так само, як і в футері. Виправлено: `ContactControls` тепер приймає `languageAlign?: "left" |
"right"` (default `"right"`) і прокидає його в `LanguageSwitcher`; виклик у `.navContacts` —
`<ContactControls languageAlign="left" />`, у `.desktopContacts` — без змін (`<ContactControls />`,
default `"right"`). Оскільки `.navContacts` видима лише до 1024px, а `.desktopContacts` — лише від
1024px, тут не знадобилась медіа-запитна логіка з `.dropdownAlignLeft` — досить статичного
`align="left"` для мобільного виклику, бо десктопна гілка того самого CSS-класу просто ніколи не
активується для прихованого елемента.

### Якорний скрол і sticky Header (scroll-padding-top)

**Знайдений і виправлений баг:** перехід за посиланнями `#services`/`#about`/`#contact` (з Header
чи Footer) підводив заголовок секції рівно до самого верху екрана, а `Header` (`position: sticky;
top: 0`, 76px заввишки) перекривав його — заголовок ховався під хедером. Виправлено одним рядком у
`globals.css`: `html { scroll-padding-top: 92px; }` (76px хедера + невеликий запас). Це нативна
CSS-властивість браузера для скрол-контейнера — застосовується автоматично до **будь-якого**
якорного переходу в межах сторінки, без потреби прописувати `scroll-margin-top` на кожній секції
окремо. Перевірено через `getBoundingClientRect()` для `#about` і `#contact`: заголовок тепер
з'являється на ~30-65px нижче нижньої межі хедера, без перекриття.

### Scroll-reveal анімації

`src/components/ui/Reveal/Reveal.tsx` — маленький клієнтський компонент-обгортка (`"use client"`,
той самий `IntersectionObserver`-патерн, що й у scrollspy Header'а): секція плавно з'являється
(`opacity 0→1` + підйом знизу `translateY(24px)→0`, 600ms) один раз, коли вперше потрапляє в поле
зору (`threshold: 0.15`), і більше не повторюється на подальших проходах скролу (`observer.unobserve`
одразу після спрацювання). Підтримує `prefers-reduced-motion: reduce` — для користувачів, які
вимкнули анімації в системі, ефект вимикається повністю (одразу `opacity:1`, без transition).

Обгорнуто в `src/app/[locale]/page.tsx`: усі секції головної, крім `Hero` (вона й так одразу видима
при завантаженні сторінки, без скролу — анімувати нема сенсу). У `src/app/[locale]/layout.tsx`
обгорнуто ще й `Footer` (спільний для всіх сторінок, включно з `/services/*`). `Header` не чіпали —
sticky, теж завжди на екрані одразу.

**Поки не поширено на секції всередині `/services/*`** (SEO-блоки, FAQ на сторінках
short-term/long-term/business) — свідомо почали з головної сторінки як першого кроку; можна
розширити тим самим компонентом пізніше, якщо ефект сподобається.

Перевірено в браузері через `getComputedStyle`: до скролу секція `opacity:0`
(`transform: translateY(24px)`), після скролу в поле зору — `opacity:1`, клас `.visible` додається.

### Адаптивність

Один брейкпоінт `1024px` перемикає layout з мобільного/планшетного стеку на десктопну композицію
(див. `src/components/**/*.module.css`, mobile-first — базові стилі без медіа-запиту вже мобільні):

- **до 1024px**: вертикальний стек, картки в 1 колонку, кнопки-CTA на всю ширину контейнера
- **від 1024px**: перекомпонована сітка — Hero, Contact і PromoBanner у дві колонки (текст+зображення
  поруч), About у дві колонки (текст+фото офісу), Advantages у ряд з 3, у `Services` — картки напрямків
  оренди в ряд по 3 (`repeat(3, 1fr)`), картки автопарку в ряд по 4 (`repeat(4, 1fr)`), кнопки стають
  компактними (не на всю ширину), Header розгортається в горизонтальне меню без гамбургера

**Знайдений і виправлений баг: горизонтальний скрол/"їзда" чорного хедера на мобільному.**
`Hero.module.css` → `.glow` (світіння навколо фото авто, `position: absolute; inset: -15%;`)
навмисно виходить за межі `.imageWrap`, щоб не обриватись різким краєм. Але сама секція `.hero`
не мала `overflow: hidden`, тож на вузьких екранах (де `.imageWrap` майже на всю ширину viewport)
цей 15%-й виліт розтягував ефективну ширину всієї сторінки за межі екрана. Це вмикало горизонтальний
скрол/панорамування (особливо iOS-«гумовий» баунс), і через це sticky `Header` (завжди на всю
ширину сторінки, чорний фон) візуально "їздив" вбік при боковому скролі — саме так це й виглядало
для користувача: "чорний прямокутник, який виходить за рамки хедера". `PromoBanner` має той самий
`.glow`-патерн, але там він уже безпечний — його `.inner` (сама картка) має `overflow: hidden` для
заокруглених кутів, і це заразом стримує виліт світіння. У `Hero` такого стримувача не було.
Виправлено: `overflow: hidden` додано на `.hero` (не на `.imageWrap` — так світіння й далі виходить
за межі фото для м'якого ефекту, але не може вийти за межі секції/сторінки). Перевірено через
скомпільований CSS — правило застосувалось.

### Умовна заборона індексації для preview-домену

Сайт ще не живе на фінальному домені, тож потрібен спосіб гарантовано не проіндексуватись
пошуковиками, поки він доступний лише на тимчасовому Vercel-домені (`*.vercel.app`) — і щоб цей
захист **автоматично зник** при переїзді на постійний домен, без правок коду.

Механізм — одна змінна середовища `NEXT_PUBLIC_SITE_ENV`:

- `src/lib/constants.ts` → `IS_PREVIEW_ENV = process.env.NEXT_PUBLIC_SITE_ENV === "preview"`
- `src/app/robots.ts` — якщо `IS_PREVIEW_ENV`, віддає `Disallow: /` для всіх user-agent (без
  посилання на sitemap); інакше — звичайний дозвільний robots.txt із sitemap, як і раніше
- `src/app/[locale]/layout.tsx` → `generateMetadata` — якщо `IS_PREVIEW_ENV`, кожна сторінка
  (успадковується від layout на всі роути, включно з `/services/*`) отримує
  `<meta name="robots" content="noindex, nofollow">`; інакше — `index, follow`
- Перевірено локально в обох режимах (`curl` на `/robots.txt` і на `<meta name="robots">` головної
  й сторінки послуги): без змінної — `Allow: /` + `index, follow`; з `NEXT_PUBLIC_SITE_ENV=preview`
  — `Disallow: /` + `noindex, nofollow`

**Налаштовано на Vercel** (проєкт `vekaro-website`, акаунт `konfirus-dot`, автодеплой з GitHub-репо
на push у `main`): `NEXT_PUBLIC_SITE_ENV=preview` і `NEXT_PUBLIC_SITE_URL=https://vekaro-website.vercel.app`
додані в Settings → Environment Variables (Production and Preview) як Config-змінні. Прев'ю-URL:
https://vekaro-website.vercel.app — перевірено `curl`: `Disallow: /` в robots.txt,
`noindex, nofollow` в meta на всіх сторінках.
